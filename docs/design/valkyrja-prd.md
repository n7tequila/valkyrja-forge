## 1. 前史：这个项目真正的起点是一套治理工具，不是 skill

`valkyrja-prd` 并非从零设计的第一件东西。它的前身是一轮关于**需求治理工具**
（`governance.py` + CI + `requirements.lock.yaml`）的五轮讨论。
本项目今天几条最核心的原则，全部诞生于那里——**skill 是那些原则的载体，不是它们的来源**。

### 三个减法（被认定为"真正的减法"而保留至今）

| 决定 | 理由 |
|---|---|
| **content digest 取代 revision 号** | 消灭"人维护元数据"这一整类漂移；且 hash 天然更强——revision 没改而内容改了照样抓得住 |
| **Source / Derived / Decision 三态分离** | 一条能长期约束系统膨胀的原则：任何人想往 YAML 加字段，先问"这是不是可推导的"，是就不许存 |
| **CI 不信任 lock、不信任 hook、一切重算** | 信任模型：唯一可信的是现算结果 |

**canonicalize 只去格式噪声、不做语义归一化**：对合规文本而言，
「必须」改成「应当」**就该**触发重审——归一化会吃掉真实的语义变更。

> 这三条今天分别活在：rebaseline 的 digest 五态比对、宪法「能推导的数据不存」、
> trace「不信任任何缓存、全部现算」。**它们比任何一个 skill 都老。**

### 两个被砍掉的 V1 组件

**`requirements.lock.yaml` 删除**——按这版自己的原则推一遍：lock 存的是 digest 快照，
快照只服务两个跨时间比对场景（审批有效性、Policy Gap），前者只需一个 hash 存在审批
字段里，后者已推到 V2。**V1 里没有任何检查会读它**。既然 CI 一切重算，
「能不存就不存」这条原则**应该先革它自己的命**。

**pre-commit hook 删除**——定位（体验优化、非信任边界）没错，但有隐性成本：
`core.hooksPath` 配置、每个开发者要装、跨平台要调、坏了要修。V1 只留 CI 一个执行点；
等团队真的抱怨「CI 才发现太慢」再补——那时也才确切知道 hook 该检查什么。

## 2. 顺序反转：本项目方法论的起源

原方案主张「先写 `governance.py` 的数据模型，baseline 模板自然确定」。
**这个顺序被明确推翻**，理由是它会导向一个陷阱：**为还不存在的文档设计解析器**。

> 当时并不知道 AI 生成的 baseline 实际长什么样、Interpretation 一节会自然写成什么结构、
> Questions 用什么格式最顺手——**这些只有真实跑一次才知道**。解析器先行意味着凭空
> 规定 markdown 约定，然后反过来强迫 AI 的输出去凑格式。

确立的三步顺序：

1. 先定**半页纸的机读语法契约**——只含 ID 正则、规则区块定界方式、
   baseline 里两节的标记格式，就这么多
2. **不带任何工具跑第一个真实 change**，人肉当 CI，眼睛做 traceability 检查
3. 拿着**真实生成的 artifact** 写 `governance.py`，让解析器去适配已验证顺手的格式

**「工具应该从实践里提取，而不是在实践前规定」**——这就是今天写在项目原则第 6 条的
「格式契约先于工具」。后来 valkyrja-spec 的 `Sources:` 行格式先实测再固化、
`trace.py` 在真实运行后才成形，都是这条的直接执行。

### 一个比所有设计问题都优先的现实问题

> **你们的 PRD 和业务规则文档，现在真的是以 markdown 形式放在 git 仓库里的吗？**

整套 digest 体系有一个沉默的前提：需求文档是仓库内可寻址、可 hash 的文本。
若 PRD 实际写在飞书/Confluence/Word 里，「BR 内容变了 digest 就变」根本无从谈起——
而那是流程习惯问题，不是工具问题，落地难度可能超过五轮讨论里的任何一项设计。
**它是第 0 步，比 ID 规则还靠前。**

### 元判断：5:0 的失衡

> 设计不复杂，但**设计产出与实践验证的比例已经失衡到 5:0**。方案质量足以支撑试点，
> 继续打磨的边际收益接近零，而几个真正的不确定点（AI 生成的 baseline 质量、
> hash 审批是恰好还是官僚、rebaseline 实际频率）**全部只能靠实跑回答**。

这条判断后来在 valkyrja-spec 上被完整复现：三轮纸面评审都没发现的三个协议缺口，
第一次真实运行全部暴露。

## 3. check 动作：一次设计重构

**需求背景**：工作区是在契约连续演进的两周里建起来的（ID 正则改过两次、
`Source` 改成 `Sources`、originals 目录拆分），存在「活的工作区 vs 演进中的契约」问题。

**关键重构**：不做「新旧 skill 版本对比」，改做「**工作区对照当前契约**」。

前者需要知道历史——哪个文件在哪个 skill 版本下生成、两版契约差在哪——
**而这些信息既没存也不该存（又是派生状态）**。后者只需两个输入：当前 SKILL.md 的契约
+ 工作区现状，diff 出来就是全部待修项；至于「为什么不符」（skill 升级还是当初写错）
**对修复毫无影响**。

> 这与 governance CI「不信任任何记录、一切重算」是同一哲学。
> 而 check 的检查清单，本身就是未来 `governance.py` 的行为规范草案——
> 现在人肉跑，跑顺了再固化成脚本。还是那个顺序。

**四条硬规则**：

1. 迁移**只改形式、不改语义**（ID 格式、frontmatter 补齐、文件移位、
   `Source`→`Sources` 可批量修；任何会动条目语义的修复不属于 check，转正常工作流）
2. **冻结的 release 永不就地修改，只报告**——旧格式 release 若需被下游消费，
   唯一出口是发「格式迁移版」（内容不变、delta 注明 format migration only），
   走正常 release 流程
3. **ID 冲突多数不可自动修**——重编号涉及宪法 8，哪个 ID 让位需要人裁决引用关系
4. 修复清单走**多项确认交互协议**

## 4. docs/ 收口：一次契约走样的修复

**问题**：SKILL.md 写死的工作区路径是 `product/initiatives/<slug>/`，
所以 AI 把它建在了仓库根下。**但这与更早议定的仓库总架构矛盾**——
原设计是三层布局 `docs/product/`（产品需求）、`docs/business-rules/`（长期业务规则）、
`docs/architecture/`，加 `openspec/` 与 `src/`，**文档统一收在 `docs/` 下**。
写 SKILL.md 时把这一层丢了。

**收口理由**：仓库根马上要住进 `src/`、`openspec/`、`tools/`、`.claude/`，
顶层再挂裸 `product/` 是命名空间污染；且 `business-rules` 将来也要进来
（Policy 层是 Policy Gap 检查的输入），它与 product 理应是 `docs/` 下的兄弟目录。

**迁移成本为零，且是有意设计的**：工作区内部所有引用要么是 ID
（`Sources`、`superseded-by`），要么是 initiative 相对路径（RN 的 `source`
指向 `others/originals/...`），**没有任何绝对路径**。整棵树 `git mv` 一条命令完事。
且必须趁**下游尚未出生**时改——等 openspec-development 写好再迁就是两头改路径
（「契约趁单消费者时改」的窗口）。

### 三层命名各司其职

| 层 | 例 | 可变性 |
|---|---|---|
| 项目文件夹（显示名） | `demo-kiosk`，连字符随意 | 可改 |
| initiative slug（目录名） | `demo_kiosk` | 可改 |
| **DOMAIN（ID 命名空间）** | `DEMO_KIOSK` | **永久冻结** |

### 「多处表述一条规则，必有一处过期」

这次走样被明确认定为**第三例漂移**，前两例是「宪法-协议漂移」与「SKILL-模板漂移」，
而这次最隐蔽——**横跨了讨论记录与 skill 两个载体**。
当时定下的对策：等 openspec-development 开工时，把仓库总布局作为显式契约写进它的
SKILL.md，**让两个 skill 引用同一份布局定义，而不是各写各的**。

> 这条教训在本项目后续反复兑现：valkyrja-spec 的 V4.8 曾同时存在于设计文档与
> `trace.py` 却漏了 SKILL.md 本体（三载体漂移，由外部评估发现）；
> catalog 条目之间用指针互引而非复述，也是同一防御。

## 5. 核心机制（**从产物重构，非决策记录**）

> 以下依据成品 SKILL.md 反推，记录「是什么」与正文自带的理由；
> **被否备选与当时约束不可考**。

- **状态机 + 八个动作**：discuss / decide / import / bootstrap / status /
  synthesize / release / check，按话语自动路由，不要求输入动作名。
- **八条宪法**：文件系统是记忆；尽快 checkpoint；Decision 只能人类铸造；
  release 只能人类触发；Accepted Decision 在其声明范围内优先；
  TM 不得创造需求；AI 只能提问不得静默补充；历史不删除。
- **STATUS.md 是唯一豁免的派生缓存**，只含最小状态、禁止统计字段，
  与扫描结果冲突时以扫描为准。
- **DISC 按话题建档而非按次数**：一话题一文件、追加式，
  正文给出的理由是「文件数量应与话题数同阶，而非与讨论次数同阶」。
- **`Q-*` 无独立目录**：编号需扫描全 initiative 的 DISC / PRD / STATUS 取最大号 +1。
  （此设计后来直接导致下游铁律「valkyrja-spec 不得铸造任何 ID 含 Q」——
  基线文件不在该扫描范围内，下游铸 Q 会造成上游静默撞号。）
- **多项确认交互协议**：>5 项时先问节奏与粒度；简略模式下疑似 DEC 仍须显示
  结论与来源（保底不可降级）；确认必须显式可枚举，沉默不构成确认。
- **bootstrap**：存量文档批量初始化，用一次完整清点报告代替逐份确认；
  核心价值是把「已经定了但没有决策形式」的事项补铸为 DEC——
  否则首次 synthesize 会依宪法 5 把已定事项错误降级进 Open Questions。

## 7. 配套工具：install-skills.sh

**设计要点**（有决策记录）：从第一天就按「**批量安装**」设计而非为单个 skill 写死路径——
因为 openspec-development 即将成为第二个 skill。源目录约定 `skills/<name>/`，
安装前校验 frontmatter 齐全（避免把半成品发布出去），
**覆盖前自动时间戳备份而非静默覆盖**。

> 备份不只是省事：每次升级留一份旧版本，万一新版契约改动后某次 check 报告看起来不对，
> 能直接翻回上一版对照——**这是为「契约漂移」专门加的一层保险**。

## 系统原型体裁（2026-08-21 增补）

**问题**：流水线里「长什么样」无人认领——PRD 管行为、arch 管工程地基、
spec 管可验收行为，首次 apply 的 UI 是 AI 现场即兴。真实项目引入外部原型
（claude.ai 生成）后暴露完整需求：收编、机检、评审、背书、演进。

**归属评估（用户裁决：并入 prd）**：新建 skill 被否——流程本体薄，
大量委托既有机制（背书=decide、注入=spec config），证据门槛不足；
并入 import 被否——话语类（文本→RN）与制品类（工件→基线包）体裁不同，
混装互相污染。落点=prd 第九动作 `prototype`，第六体裁目录
`initiatives/<slug>/prototype/`（original/vN 原件 + vN 背书基线包）。

**四步协议**：收编（拆壳+机检，**清单必须从 release 机读区提取带 FRID 锚点，
不得凭记忆**——两次真实踩坑：凭记忆的清单让原型忠实继承作者的记忆漏洞，
凭记忆的 REQ 编号让 DEC 引用错块、被发版 digest 越界断言捕获）→
评审（三层拆解：观感→迭代 / 行为→DISC 回流 / 标定→需求链；
原型不得成为第二需求源）→ 背书（decide 铸 DEC + 基线包；未背书=参考材料；
尺寸权威不转移给图稿像素）→ 演进（版本化 + supersede 链 +
视觉回归测试为实现侧机检载体）。

**实证**：试点项目 v1→v3 三轮迭代驱动本协议成形——v2 机检 25/25 过 release
UI 清单、暴露 1/3 界面规则过猛（原型评审的预期价值：真实渲染否掉纸面规则）；
评审反馈经三层拆解产出 DISC-006/007/008 → DEC-020/021/022 → release v1.2，
V2.5 发版欠账门限全生命周期（不触闸→合拢→清零）随之首次实战。
