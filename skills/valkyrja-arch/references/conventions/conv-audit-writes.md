# 审计写入约定

> 审计的三个死穴恰好分布在三层：**存储可篡改**（等于没审计）、
> **时序错误**（幽灵记录或静默丢失）、**测试假绿**（长期失效无人知）。
> 本条把三层解法钉在一起——单独做对任何一层都不够。

## 记录内容

每条审计事件最少含：操作人、时间戳、事件类型、实体类型 + 实体 ID、
requestId（关联全链路日志）、来源 IP（如适用）。
业务快照放扩展字段（JSONB 类），**核心检索维度必须是独立列**（时间/人/类型/实体）。

## 存储：不可篡改

- 审计表用数据库触发器**禁止 UPDATE / DELETE**（应用层权限控制不算数——
  审计防的就是拥有应用权限的人）。
- 保留期清理走独立的受控通道（分区滚动/归档任务），不开放行级删除。
- 特殊类型绑定陷阱见 conv-db-relational-postgres（真实事故：IP 列
  INET 绑定错误让审计静默失效数轮 review）。

## 时序：AFTER_COMMIT + 三层防御

审计是「业务事务后副作用」的典型，**必须**遵循 conv-java-ddd 规则 10
（时序/隔离/吞咽三层，及 AFTER_COMMIT 回调链的 REQUIRES_NEW 推论）——
此处不复述，权威在彼。审计特有的补充：

- 吞咽层吞掉的审计写入失败**必须 WARN 日志留痕**（见 conv-logging-context）——
  审计丢失本身是需要被审计的事件。
- 审计失败不阻断业务是默认取舍；若某类事件法规要求「不落审计即失败」，
  该类事件改为业务事务内同步写，**并显式记入项目绑定**——两种模式不混用默认。

## 触发方式

- 声明式优先（注解/装饰器标注在应用服务方法上），切面统一采集——
  散落在业务代码里的手工 `auditLog.write()` 必然漏。
- 实体 ID 的提取规则显式约定（从返回值/参数的哪个字段取），
  非常规方法签名出现时扩展提取器，不静默跳过。

## 测试：反假绿三件套

1. 双断言时序 IT：commit → 恰好 1 条；rollback → 0 条（conv-spring-testing §3）
2. 切面测试显式开代理（§1）——否则测的是没有审计的世界
3. 断言用相对计数，禁止 cleanup DELETE 审计行（§5）

## 采纳时须绑定的项目参数

- 事件类型清单与命名（建议 `<实体>_<动作过去式>`：`ORDER_CREATED`）
- 保留期与清理通道
- 「必须同步落审计」的事件清单（若有）
