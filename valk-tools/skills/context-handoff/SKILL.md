# 上下文交接

长会话会漂移：早期的裁决被后期的推测覆盖，而人看不出来。交接不是为了省 token，
**是为了让下一轮从事实重新起步，而不是从一段被压缩过的记忆里起步。**

两个方向：**存**（本轮结束时）与**取**（新会话开头）。

## 何时该交接

- 用户明说要清空。
- 窗口接近上限而任务未完。
- 刚完成一个自然段落（一个任务收口、一批问答过完），**这是最好的时机**——
  段落中间交接会留下半截状态。

## 存：四步

### 一 · 先让工作树干净

**未提交的改动在清空后就是无主孤儿**——新会话不知道它们为什么在那里、做完没有。

跑一次全量验证并**核对退出码**，然后提交。验证不过就不要交接，先修；实在修不完，
在交接记录里明确写「当前构建是红的，红在哪」。

### 二 · 更新持久记忆

主记忆写**怎么恢复**，不只是做到哪。必备五项：

| 项 | 要点 |
|---|---|
| 恢复入口 | 新会话先读哪个文件、跑哪条命令；**两处冲突时以哪个为准** |
| 当前位置 | 进度数字，以及它从哪查得到 |
| 下一件事 | **连同理由**——为什么是这个顺序，谁依赖谁 |
| 悬着的事 | 阻塞项、等外部回复的、跨任务契约 |
| 铁律 | 这个项目里做错过、不能再错的 |

**下一步的理由最容易丢，也最值钱。** 只写「下一件事是 A」，新会话不知道 A 为什么排在 B 前面，
很可能换个顺序重做一遍判断。

其他值得单独成篇的：反复出现的工作方式（用户的偏好、固定回路）、一次性的重要澄清。
**别把仓库已经记录的东西抄进记忆**——代码结构、提交历史、规格条文，那些查得到。

### 三 · 仓内留一份

记忆是给 AI 的，仓内日志是给人的，两者都要。仓内那份按项目既有体例写
（迭代日志、进度表、决策记录），它同时是给协作者和未来的自己看的。

### 四 · 给续接提示词

交接完了要给用户一段**可以直接粘贴**的提示词。写法见下。

## 取：新会话怎么起步

**先读，再动。** 顺序是：持久记忆 → 记忆指向的仓内文件 → 用命令核对真实状态。

**核对这一步不能省。** 记忆写的是当时的判断，可能已经过时；命令查出来的是现在的事实。
两者冲突以事实为准，并且**当场改记忆**。

例如进度：记忆说 33/54，就去跑一句 grep 数未完成项，对不上就以文件为准。

复述三到五句当前状态给用户，再开始干活。

## 续接提示词怎么写

给用户的那段话要能独立成立——**新会话看不到本轮的任何内容**。

```
继续 <项目名> 的工作。

先读 <记忆入口>，再读 <仓内交接文件>，然后跑 <核对命令> 确认真实进度。
记忆与文件冲突以文件为准。

上一轮做完：<一句话>
下一件事：<具体任务>，理由是 <为什么是它>
注意：<最容易踩的一两条>
```

不要写「继续上次的工作」——新会话不知道上次是什么。
不要把裁决过的结论重新写成待议项——那会让人再答一遍。

## 三条纪律

**记忆里的每个数字都要能查证。** 写「33/54」就要说清它从哪查；写「下一件事是 A」
就要说清依据。查不到出处的数字，下一轮会被当成事实继续传下去。

**不要在交接记录里写预测。** 只记已发生的事和已作出的裁决。「预计明天完成」这类会变成
下一轮的假前提。

**交接记录要能被覆盖。** 主记忆是活的，每次交接重写，不要不断追加——追加会让它长到
没人读完，那时它就失效了。旧交接点可以留一两行摘要，多的删掉。
