# 描述协议：固定块与话术

确认时的描述是决策材料，不是分析报告。读者要在一分钟内定「是、否、改」。
所以每条只回答做决定需要的问题，顺序固定，读到哪一行都能停。
同一个块既是报告条目也是确认材料，不写两遍。读者设定：没读过本技能的工程师。

## 完整块（Level 2、Level 3 用）

```
REF-012 · <一句话标题：说问题，不说模式>

现象  在 {文件:行}，{做某件具体的事} 需要 {改几处 / 穿过几个分支}。
压力  过去 {N} 个月这段被改 {k} 次；上次「新增 {某类型}」的提交碰了 {m} 个文件。
      没有历史证据时必须写：「无历史证据，属推测」。
代价  不改的话，下一次 {已知的具体需求} 你要改 {A、B、C}，其中 {C} 编译器不会提醒你。
目标  改完后同样的需求只需 {新增一个类 / 改一处}。结构前后对照，最多十行。
      更简单的做法是 {某手法}，它能解决 {X} 但解决不了 {Y}，所以才到这一层。
步骤  1. {手法名} {对象}，IDE 执行，跑测试。   每步一个提交，步间全绿。
      2. …
      超过 8 步先拆条；写不出步骤就不是重构，结论改 REWRITE。
兜底  档位 {一/二/三}；{测试类} 覆盖 {将被移动的分支}；缺 {哪些}，第 0 步先补。基线全绿。
影响  碰 {n} 个文件；改 {k} 个公开签名：{列名}；调用方 {m} 处：{列名}。
      不碰数据库、不碰 API 契约、不碰事务边界。碰到哪个就写哪个。
风险  类型先验 {低/中/高}；可能出问题的机制是 {具体机制}；靠 {哪些测试} 发现；
      出事回退到第 {n} 步的提交。
不做  本次不做 {X}，因为 {原因}。发现疑似 bug：{列出}。不顺手修，另开条目。
时机  First / After / Later，一句话说为什么是这个时机。
问题  现在要你定的是：A {方案} / B {更简单的方案} / C 改。
```

## 每行的话术

示例用一个虚构的运费计算模块，与任何真实项目无关。

| 行 | 合格的写法 | 不合格的写法 |
|---|---|---|
| 现象 | 「在 `ShippingFeeCalculator.calc` 第 40 到 130 行，新增一种运费规则要在同一个方法里加分支，并同步改 `FeeType` 枚举和 `FeeValidator` 两处」 | 「职责不单一」「方法太长」 |
| 压力 | 「近 12 个月改 9 次；上次加 `OVERSEAS` 的提交碰了 4 个文件」 | 「经常改」「以后还会加」 |
| 代价 | 「下一个已知需求是同城次日达，要改 calc、FeeType、FeeValidator 三处，漏改 FeeValidator 不报编译错」 | 「不利于扩展」 |
| 目标 | 「新增运费规则只需加一个 `FeeRule` 实现类。更简单的做法是 Extract Function 把三个分支体抽成私有方法，它能让 calc 好读，但三处同步修改还在」 | 「引入 Strategy 模式」 |
| 步骤 | 「1. Extract Function：每个分支体抽成私有方法，IDE 执行，跑测试。2. Move Function：把私有方法搬进各自的 FeeRule 类 …」 | 「重构成策略模式」 |
| 兜底 | 「档位三。`ShippingFeeCalculatorTest` 覆盖 5 个规则里的 3 个，缺 OVERSEAS 与 BULK；PIT 在该类存活突变体 7 个。第 0 步先补两条特征测试」 | 「有测试」「覆盖率 80%」 |
| 影响 | 「碰 6 个文件；改 1 个公开签名：`calc(Order)` 变 `calc(Order, FeeContext)`；调用方 3 处：OrderService、QuoteService、ReportJob」 | 「影响较小」 |
| 风险 | 「先验中；机制：calc 带 @Transactional，第 3 步挪到新类后若从同类内部调用会绕过代理；靠 OrderServiceIT 的回滚用例发现；出事回退到第 2 步提交」 | 「低风险」 |
| 不做 | 「不改 FeeValidator 的校验顺序。发现 BULK 规则对负数重量不报错，疑似 bug，列附录」 | 「顺便把日志格式统一了」 |
| 时机 | 「First：同城次日达下周开工，先把缝抽出来，那条需求就变成一处改动」 | 只写「First」不给理由 |
| 问题 | 「A 走到 FeeRule 接口加 5 个实现 / B 只做 Extract Function 保留 switch / C 你改」 | 「你觉得呢？」 |

## Level 1 单行形式

```
REF-021 · Extract Function · OrderService.place 第 88 到 140 行抽成 validateStock() · 不改签名 · OrderServiceTest 覆盖 · IDE 执行
```

批量清单末尾一句：「以上 N 条全部执行 / 排除编号 … / 全部跳过」。

## 短块

```
REF-030 · KEEP
现象  LocalFileStorage 是 FileStorage 接口的唯一实现。
判断  接口没有形成真实的缝。
原因  但它是注入边界且测试里有 mock，删接口收益为零、改动 11 处。不动。
```

```
REF-031 · REJECT
候选  Builder。
判断  不加。
原因  对象只有 4 个参数、构造无顺序约束；Builder 只会多一个类。参数到 6 个以上再议。
```

```
REF-032 · TESTS_FIRST
现象  NotificationDispatcher.send 按渠道 switch 五路，且同一 switch 在 retry() 里再出现一次，符合 Repeated Switches。
缺什么  该类无测试；五路里三路调外部 SDK。
先做  按 safe-change.md 生成特征测试钉住五路输出；补完再评是否走到 Level 3。
```

```
REF-033 · REWRITE
现象  ReportExporter 读写共享静态状态，导出格式要从 CSV 换成 XLSX 且列语义要变。
判断  行为必须变，且拆不出保行为的小步。这不是重构。
建议  按 safe-change.md 的 Branch by Abstraction 在缝后面重写；另开条目裁决。
```

## 确认问句

| 级 | 问句形状 |
|---|---|
| Level 3 | 「这条要定形状：A {模式路径} / B {更简单方案} / C 你改」。一次一条，等裁决再出下一条 |
| Level 2 | 「是否接受 {手法} {对象}：是 / 否 / 改成 {替代}」。按依赖序一次一条 |
| Level 1 | 「以上 N 条：全部执行 / 排除编号 … / 全部跳过」 |
| 短块 | 不问；末尾一句「以上 KEEP / REJECT 如要推翻，写编号即可」 |

## 出示前自检

- 十二条原则逐条过。
- 标题里没有模式名。
- 每个恶名词后面跟着一个代码里看得见的实例。
- 压力行有数字，或写了「推测」。
- 步骤行每步一个手法名，步数不超过 8。
- 兜底行写了档位和具体测试名。
- 影响行是名字不是形容词。
- 风险行有先验也有机制。
- 时机行有理由。
- 最后一行是问题。
