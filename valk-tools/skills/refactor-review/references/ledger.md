# 重构台账

重构不是一次做完的事。一次审查裁掉的 KEEP、推迟的 Later、缺测试的 TESTS_FIRST，都是下一次
审查的起点；不记下来，下次从零扫一遍，还很可能裁出不一样的结论。台账让三件事成立：
裁过的不再问第二遍；推迟的带着触发条件，到点会响；做了的能对上提交号。

台账是本技能**唯一落盘的东西**。它记的是裁决，不是代码，「只审不改」不变。
写之前回显路径与内容，用户明确「确认」才写。

## 文件在哪

按顺序找，命中第一个就用：

1. 用户给的路径。
2. 仓内已有的 `refactoring-ledger.md`（任意目录；跳过 node_modules、target、build、dist、.git）。
3. 前五行含 `refactor-review ledger` 字样的任意 `.md`——用户改过名的台账。

都没有就新建：仓里有 `docs/` 放 `docs/refactoring-ledger.md`，没有放仓根 `refactoring-ledger.md`。
**不新建目录。** 一个仓一份，多模块仓也是一份，条目自带范围路径。

## 格式

三段：在案（还没结的）、已结（一行一条，防止下次重问）、记录（每次审查或对账一块，只追加）。
编号 REF-xxx 跨次连续，从台账里最大的编号往下接。示例是虚构的运费模块。

```
# 重构台账
```

## 状态

| 状态 | 来自 | 转出 |
|---|---|---|
| 待做 | REFACTOR 确认；时机在块内时机行 | 对上提交 → 已做；用户改主意 → 撤销 |
| 待测 | TESTS_FIRST | 测试补上 → 重评，结果写新裁决 |
| 另议 | REWRITE | 走别的流程；台账只记有这回事 |
| 观察 | KEEP / REJECT 带触发；用户裁「不做」的 REFACTOR | 触发 → 重评 |
| 待裁 | 出示时「先放一放」、收尾前没回来裁的 | 下次简报原样再出 |
| 不动 | KEEP 不带触发：当作 API、计划删除 | 直接进已结；位置有改动才重评 |
| 已做 | 对账确认 | 终态 |
| 撤销 | 用户推翻、文件已删、需求没了 | 终态 |

## 每条进台账的形式

- **待做 / 待测 / 另议**：确认过的完整块或短块原样进，问题行换成裁决行，顶上加状态与范围。
  执行的人要看步骤、兜底、影响、风险、回退点，少一样就得重新推导。
- **观察**：五行——标题、状态、范围、触发、裁决。
- **待裁**：完整块原样进，问题行保留。
- **不动**：一行进已结，写原因。
- **Level 1**：单行形式，每条一行加状态，同一次的归一个批次标题下；批次下没在案条目了就删标题。

## 观察哨

观察哨（不动代码，只记下什么条件出现时回头看）是「条件 → 动作」，不是推测。
十二条原则里第 3、4 条禁的是拿推测当现在动手的理由；观察哨相反，它把「现在不动」的
理由写成可核对的条件。触发条件只有三种合法形式：

- 数字：「构造参数到 6 个（现 4）」「calc 到 65 行（现 58）」「第三个实现出现」。
- git 事件：「下次有提交同时碰 A 和 B」「这个 switch 再被改一次」。
- 点名的需求：「同城次日达排上时」。

「以后可能」「业务扩展时」不是触发条件；写不出可核对的条件，就标不动。
触发行定死为「条件 → 动作」，例「有需求碰 Notifier → 先补特征测试」；只有动作没有条件的不算。

三处产生观察哨：

- 每条 KEEP / REJECT 的短块必须带触发行，或写「触发  不动（原因）」。
- 取证量到的数字接近阈值但没到：行数到阈值八成、Rule of Three 差一个到三、热点类无测试。
  不成候选、不出块，直接以观察状态进台账（有编号）。
- 用户对 REFACTOR 裁「不做」：转观察，触发写用户说的条件；没说就问一句。

## 对账

台账存在时，定范围之后、取证之前做，结果进简报的「台账」行。逐条按状态：

- **待做 / 待测 / 另议**：`git log <记录提交>..HEAD --oneline -- <范围文件>`，记录提交是
  裁决所在记录块头上的哈希。
  有 `refactor:` 提交且信息带该编号 → 拟已做，记提交号。
  有 refactor 提交但不带编号 → 重读现象位置：味没了拟已做并标「推断」，味还在写「未动」。
  文件已删 → 拟撤销。拟已做时对一下计划：提交数或手法与步骤行不一致，记录块写一行「偏离」；
  一致不写。
- **观察**：重新核对触发条件——数字重新量，git 事件重新查，需求型的合成一问
  （「上次留的需求：X 排上了吗 / Y / Z」）。触发 → 进本次候选重评，简报标「触发」；
  没触发 → 保持，更新括号里的现数。
- **待裁**：原样进本次候选，简报行尾标「待裁」。
- **不动**（已结里）：`git log <记录提交>..HEAD -- <文件>` 为 0 → 不再列；不为 0 → 重评。

拟出的状态变更不单独问，和写台账一起确认。用户说「更新台账」「对一下台账」时只做这一步
加收尾，不开新审查。

## 收尾

Level 1 批确认完、汇总一屏之后，紧接着提议写台账，一次只问这一个问题：

- 有台账：回显「新增 k 条、关闭 m 条、改状态 j 条」和本次记录块全文；在案增删改、已结追加、
  记录追加。
- 没有：回显默认路径和整个文件。
- 只对账不审查：记录块只有对账行与偏离行，头上标「对账」。
- AskUserQuestion：写入 {路径} / 换路径 / 这次不写。「这次不写」就只留对话里的汇总。

写完回一行：路径、在案几条、观察几条、下次建议。

## 没有值得动的时候

结论全是 KEEP / REJECT，或根本没有候选，仍然走收尾：台账里进的是观察哨与「下次」行，
简报用 description-protocol.md 的「空结论简报」。「没有值得动的」是结论，不是没产出——
下次审查从这些观察哨开始，比从零扫便宜得多。

「下次」行写两件事。什么时候再审只有两个来源：观察哨触发，或用户亲口说的下一个模块——
模型不猜排期，没有就只写第二件：哪些不用再审（近 12 月零改动的、当作 API 的）。
