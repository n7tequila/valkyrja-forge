# 安全改动方法

目录告诉你改什么，这个文件说怎么改才不出 bug。这是决定重构成败的那一半。

## 三条法则

1. **重构不改可观察行为。** 行为要变就是功能改动，另开条目、另写测试、另起提交。
   可观察行为包括：返回值、异常类型与抛出时机、副作用顺序、事务边界、序列化形状、并发语义。
   日志默认不算，但被告警规则或审计依赖的日志算，动它之前先问。
2. **重构与修 bug 不进同一个提交。** 审阅者分不开两者，回退会丢掉错的那一半。
3. **测试不绿不重构。** 基线红的先修基线或另开条目；否则分不清是重构弄坏的还是本来就坏。

## 循环

绿。做一个小手法。还绿吗？是，提交；否，立刻回退。味消失了吗？否，下一个手法；是，停。

- **回退，不调试。** 一步之后红了说明步子太大。回退几秒钟，调试半成品结构一下午。
- **每个有名字的手法一个检查点。** 「抽出 calcDiscount」「卫语句进 process」，不是每行一个，也不是整个重构一个。
- **一步一提交**，提交信息 `refactor: <手法> <对象>`。40 个小绿提交可以审、可以二分、可以部分回退；
  一个 4000 行的「重构」只能整体信任或整体拒绝，而审阅者总是选择信任，bug 就是这么上线的。

## 没有测试时

遗留代码的常态。死锁是：没测试不能安全重构，不重构又写不了测试。按这个顺序解开。

### 特征测试

写测试记录代码**现在**做什么，包括 bug。不是断言正确性，是把行为钉住，动了能看见。

1. 用真实输入调用代码。
2. 断言一个明知错的值。
3. 跑，失败信息告诉你实际值。
4. 把实际值贴进断言。
5. 重复，直到重要路径都钉住。

**生成，不手写。** 对数据函数写一个一次性脚本（脚本不入库，只入库用例文件与测试），用当前代码跑
10 到 20 个代表性输入（每个分支、每个边界、空值），把实际输出冻成用例文件。**严格相等，含类型**：
int 0 变成 double 0.0 正是重构会引入、宽松相等会放过的漂移。

**发现 bug 不修。** 钉住错误行为，记下来，另开条目。下游可能依赖这个 bug。钉住的期望值
**只在修 bug 的提交里、一次只动一个用例**地改；不要重跑生成器整体重钉，那会连带接受所有别的漂移。

### 找缝

Feathers 的定义：**seam 是不在该处编辑就能改变行为的位置**，每条缝有一个 enabling point。
Java 里最常用的是对象缝：构造器参数、setter、可覆盖的方法。解依赖手法（Feathers 第 25 章，24 个）
里最常用的：Parameterize Constructor、Extract Interface、Subclass and Override Method、Adapt Parameter。
这些手法本身也是重构，但此处目的只有一个：让测试能进来。

### Sprout 与 Wrap

没时间钉住整段旧代码时：**Sprout Method / Class** 把新逻辑写在新方法或新类里，旧代码只加一行调用，
新代码有测试；**Wrap Method / Class** 把旧方法改名后用同名新方法包住，在新方法里加行为。
两者都不碰旧逻辑本身。

## Parallel Change（expand、migrate、contract）

改任何**有你不控制的活调用方**的东西：跨仓的方法签名、公开 API、消息格式、数据库列。

1. **Expand**：新的加在旧的旁边。新参数带默认值、新方法与旧方法并存、新列与旧列并存。
2. **Migrate**：调用方一个一个搬到新形状，每步可发布。
3. **Contract**：确认没人读旧的再删。「没人」用日志或流量证明，不只靠 grep。

代价是两种形状并存一段时间，而且 contract 这一步最常被忘。给它一个日期或工单；只 expand 不 contract
就是永久重复。Level 2 里所有改公开签名的条目，步骤行默认按这三段写。

## 预备性重构

Kent Beck：先让改动变容易（注意，这可能很难），再做那个容易的改动。

一个落在乱代码上的需求是两件工作：先在自己的提交里重构，直到需求变成一处小改动；再在自己的
提交里加需求。**两者不进同一个 diff。** 范围限定在需求的脚印内：它要扩展的方法、要调用的类，不多一步。
抽出来的缝是否进一步变成模式，是门禁的另一个决定；多数时候缝就够了。

## 大改动：Mikado

一次坐不完、「先动手」会让树坏好几天的改动。

定目标。天真地试。测试绿吗？是，提交，完；否，把卡住的东西记为前置条件，**全部回退**，
挑一个叶子前置，再试。

纪律在回退。每次尝试结束时树是干净的，手里多了一张前置依赖图。然后做叶子，每片叶子小、
可独立发布、绿。主目标在叶子做完后几乎自动落下。

## REWRITE 的路径

重写不是重构，但也不必大爆炸。

- **Branch by Abstraction**（Hammant 2007，Fowler 2014 命名）：先在旧实现前面立一层抽象，把调用方切到
  抽象上；在抽象后面建新实现；逐个切换；删旧实现，最后视情况删抽象。全程主干可发布。
- **Strangler Fig**（Fowler 2004，2019 改名）：新系统包在旧系统外面，逐个截获功能，旧系统被慢慢绞死。
  适合整块子系统的替换。
- 两者都以 Feathers 五步法开头：找改动点、找测试点、解依赖、写测试、再改。

## 何时不重构

- 当作 API 用、永远不会改的丑代码。不碰，纯风险无回报。
- 计划删除的代码。
- 你还不理解的代码。先读，先写特征测试，再动。重构不是理解的替代品。
- 截止日期压顶且钉住行为的代价超过期限。那就 Sprout 或 Wrap 新代码，记债，排期。
  没有「没时间所以不写测试直接改结构」这个选项，债就是这么来的。
- 行为必须变。那是 REWRITE 或功能改动。

## 度量

重构的收益是未来改动变便宜。可用的弱代理：一次提交平均碰几个文件（Shotgun Surgery 先在这里下降）；
最差方法的圈复杂度；改动行的测试覆盖而不是全局覆盖；该区域改动的前置时间。
都不是目标，直接优化任何一个指标都会得到迎合指标的代码。看几个月的方向，不给单个 PR 打分。
