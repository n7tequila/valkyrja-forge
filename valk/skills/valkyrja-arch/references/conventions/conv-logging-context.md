# 日志约定（上下文 · 粒度 · 内容）

## 请求上下文贯穿

- 每个入站请求绑定 **requestId**（客户端传入或服务端生成，UUID），
  同时出现在：响应头、响应体信封、该请求产生的**每一行日志**。
  这是"用户报错截图 → 定位全链路日志"的唯一可靠通道。
- 上下文键最小集：`requestId`；有认证后追加 `userId`（未登录留空）；
  多实例部署追加实例标识。项目可增键，**不可减**。

## 实现模式（线程/任务上下文，如 MDC）

```
入口 Filter/Middleware：
  写入上下文 → try { 处理请求 } finally { 清除上下文 }
```

- **finally 清除是硬要求**——线程池复用下不清除 = 上下文串号，
  A 用户的日志挂着 B 的 requestId，排障时指向完全错误的方向。
- 异步/线程切换处上下文**不会自动传播**：任务提交处显式捕获与恢复
  （装饰 executor 或任务包装），否则异步段日志上下文为空。

## 事件粒度：一个请求一条权威日志

- 默认形态是 **canonical log line**——请求在本服务处理结束时输出一条高信息
  密度日志，把该请求的关键事实（谁、做了什么、结果、耗时、关键业务 ID、
  依赖调用次数）平铺成字段。这样「状态码 ≥500 且耗时 >3s」一条查询就能出
  结果；散落的碎片行做不到，因为条件分布在互不关联的多行里。
- **禁止自动生成 `enter X` / `exit X` 式的流程日志。** 这是 AI 写日志最典型
  的失效形态：行数暴涨、单行信息密度趋零、真实异常被噪声稀释，且日志量直接
  变成存储与检索成本。方法进出用 trace / profiling 工具看，不用 INFO 打。
- 中间过程要留痕时，**优先往 canonical line 上挂字段，而不是新增一行**
  （如 `dbQueries=4`、`cacheHit=true`、`retries=1`）。
- 请求内只有两类情况可以单独成行：①需要人处理的异常（ERROR）；
  ②已自动降级但需知晓的分支（WARN）。两者都必须带上下文键。

## 字段命名稳定性

- canonical line 的字段名是**对外契约**。一旦被查询语句、看板、告警规则依赖，
  改名的代价是下游同时失效且**静默**——告警不会报错，只会不再触发。
- 字段名一次定死并记入下方项目参数节（如 `requestId` / `userId` /
  `durationMs` / `httpStatus`）。**新增字段可以；改名或改语义等同破坏性变更**，
  须走与接口契约同级的变更流程。
- 同一事实全项目只有一个字段名。`userId` 与 `uid` 并存 = 之后每条查询都得写 OR。

## 值得记录的事件（正面清单）

至少覆盖：认证成功与失败、授权拒绝、输入校验失败、应用异常、安全相关事件
（权限变更、敏感数据导出）。

- 反过来，**不在清单上的默认不记**。过量日志的代价不只是存储——真实异常被
  噪声稀释后，排障时间反而变长。
- 校验失败记「哪个字段不合法」，**不记字段值本身**：用户输入可能正是口令或证件号。

## 开发期临时日志

- 调试用的临时日志**不进提交**。本地随便打，进 PR 前清掉；代码审查把
  「新增的 INFO 行是否有长期价值」列为必查项。
- 需要长期保留的排障日志用 **DEBUG 级 + 生产默认关闭**，不要用 INFO 混过去。
  用 INFO 打调试信息是「临时变永久」的标准路径——量堆起来之后没有人敢删。
- 禁止把打印语句（`System.out` / `print` / `console.log`）当日志用：
  它们绕过级别控制、绕过上下文键，容器里还绕过采集配置。

## 输出格式

- 日志 pattern 必须包含上下文占位（如 `[%X{requestId}]`）——
  只写进 MDC 不进 pattern 等于没做。
- 结构化输出（JSON 行）时上下文键平铺为顶层字段，便于日志系统索引。
- 日志调用一律用**占位符模板**，禁止字符串拼接：
  `log.info("record created, recordId={}, userId={}", recordId, userId)`。
  两个原因：①拼接在该级别关闭时仍然求值，是热路径上白付的开销；
  ②结构化采集靠模板才能把参数还原成字段，拼接后只剩一整条字符串。
- 容器化部署写 **stdout/stderr**，由平台采集；应用内不自管日志文件与轮转
  （容器重建即丢，且应用与平台两套轮转策略会互相打架）。

## 内容纪律

- **一律不入日志**：口令、access / refresh token、会话标识、私钥与加密密钥、
  数据库连接串、Authorization 头与 Cookie 原文、完整证件号、完整手机号。
  需要关联时记录 ID 或不可逆摘要。根因：日志的访问面远大于业务库——采集链路、
  检索系统、告警通道、导出的排障文件都是副本，任何一处的权限都可能更宽。
- 错误日志必须带异常堆栈与上下文；**禁止 `catch` 后只打一行 message**
  （丢堆栈 = 丢现场）。
- 级别语义：ERROR=需要人处理的异常；WARN=已自动降级/吞掉但需知晓
  （被吞掉的副作用失败**必须**至少 WARN，禁止完全静默）；INFO=关键业务节点；
  DEBUG=默认关闭。

## 采纳时须绑定的项目参数

- 上下文键全集与 requestId 头名（与 API 信封约定一致）
- pattern / JSON 字段模板
- **canonical line 的字段全集**：字段名、类型、哪些必填
- **可单独成行的事件白名单**（在上面正面清单基础上按项目追加）
- 脱敏字段清单与脱敏格式（在上面禁入清单基础上追加项目特有项）
- 日志去向与保留策略（stdout 还是文件、保留期、DEBUG 在哪些环境开启）
