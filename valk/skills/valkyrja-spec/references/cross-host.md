# 跨宿主交叉开发：交出 apply 与复审（详版）

> **何时读本文件**：用户要把某个 change 的 apply 交给另一宿主、要求复审（review）、
> verify 壳结束后风险信号命中要提示复审、或实施中遇到疑似规格空缺/技术契约冲突时。
> SKILL.md 只保留摘要与路由；步骤、模板与判别在这里。
> 设计理由与被否决的方案见 `docs/design/valkyrja-spec.md`「跨宿主交叉开发」节（forge 仓内，不随技能分发）。

## 一、原则：不新增真相源

- **change 目录就是交接物。** proposal（Requirement Authority）、design（`依据:` 标注）、
  tasks、spec delta 已经承载「做什么、依据什么、做到哪」；不另建交接包、状态机、
  事件日志或路由配置。流水线位置一律由 `next` 从磁盘现算。
- **确认不随提示词转移。** 交出方出示过的 apply 确认只对交出方那一刻成立；
  接手方现场重跑 pre-apply trace、重新出示确认。提示词不是放行凭证。
- **单写者。** 交出后交出方不再写这个 change；同一 change 同一时刻只有一个宿主在写。
  这是协议约定，不是锁。
- **宿主对称。** Claude → Codex 与 Codex → Claude 同一套规则，谁规划谁实施由用户按任务定。
- **分工。** 实施方做 apply 与 verify 壳（含官方 verify）；复审由另一宿主做，规划方不重做 verify。
  复审建议在新会话里做，避免与写规划的上下文共享盲区。
- **下一步不靠用户记。** 每个环节结束时都写明下一步与对应调用名；需要换宿主时直接给出可粘贴的提示词。
- **提示词一律用接手方的调用名。** 四种写法：Claude Code plugin `/valk:spec`（`/valk:prd`、`/valk:arch`）、
  复制安装 `/valkyrja-spec`；Codex plugin `$valk:valkyrja-spec`（`$valk:valkyrja-prd`、`$valk:valkyrja-arch`）、
  复制安装 `$valkyrja-spec`。不确定接手方怎么装的，请用户在接手方的技能列表里核对。
- **不额外往规格文件里写流程提醒。** 下一步提示写在对话与提示词里。官方 schema 允许的
  tasks.md 末尾 `## Workflow follow-up`（普通列表、不计进度）照常保留；本技能自己只追加复审组（见第四节）。
- **需要后续动作的信息，在会话结束或交出前落到既有归宿（分流）**；不另建交接文件，提示词引用归宿而不复述：

  | 信息 | 归宿 |
  |---|---|
  | 复审结论、A 类返工 | tasks.md 复审组（第四节） |
  | B/C 问题与裁决理由 | 裁决产出的 DEC / ADEC（其 Context） |
  | 不阻塞的工程备注（将来某条件成立时要做的事） | 经 valkyrja-arch 确认记入 `docs/architecture/backlog.md`，写明触发条件 |
  | 不阻塞的产品疑问 | 经 valkyrja-prd 记为待澄清问题 |
  | 「已有权威可答、只需修正」的处理 | 修正提交的提交信息写明依据 |

  只在对话里出现、没有落到任何归宿的信息，视为会随压缩或换会话丢失。
- **交接点默认提交**：交出 apply 前、交出复审前、返工完成后，默认提议提交——回显将提交的文件与提交信息，
  经用户确认后提交，范围由此能写成 `<base>..<提交>`。第三节的「直接修正」单独提交，提交信息写明依据与用户确认。
  用户明确不提交时，提示词与复审范围写「工作区」并注明原因（真实运行：只作建议时四个 change 有三个整批未提交，
  复审范围只能写工作区，一次复审还因此把经确认的修正误判为擅自修改）。
- **只能由人做的验证**（真实终端交互等）：规划时写进 `## Workflow follow-up` 普通列表，不写成任务；
  已写成任务的，智能体做完能做的部分后**不勾选**，标「待人工验证」并给出命令与临时数据要求，
  等用户说明已做后经确认勾选。这类验证交给用户，不转给另一宿主；归档回显列出仍待人工的验证。
- **勾选按任务原文执行的验证**：任务写明的验证命令按原文执行；实际跑的命令与原文不同（如额外设了环境变量）时
  不勾选，或在报告里写明差异——不用另一条命令的结果为原文打勾（真实运行：带 PYTHONPATH 跑通后，
  为不带 PYTHONPATH 的原文命令打了勾，命令其实跑不通）。

## 二、交出 apply

1. **出示时机。** 只在 apply 确认回显处作为一个选项出现：pre-apply trace **本次现跑放行**、
   且规划自检（SKILL.md propose 壳）没有待裁决项后，
   用户可选「在本宿主 apply」或「交给另一宿主 apply」。apply 进行中（含复审返工后）同样可交。
   交出本身只产出文字、不写盘，不是特权动作，无需另行确认。
2. **盘点现场（只读）。** 列出 `git status --short` 的未提交文件；确认本会话没有仍在运行的
   写入任务（后台测试、子 agent、未返回的工具调用）。仍有写者时先报告，不声称可以交出。
   不代用户 stash / commit / checkout / 清理。
3. **未提交改动的处理。** 按第一节默认提议提交；当前宿主装有 valk-tools 时可建议
   顺带用 `host-handoff` 采集状态指纹供接手方核验；用户不提交时在提示词里列出未提交文件清单。
   本技能不依赖 valk-tools：未安装时直接走另两种处理，不为交出而建议安装。
4. **输出提示词**（开头用接手方调用名，见第一节）：

   ```text
   <接手方调用名> next：接续 change <change-name> 的 apply（由 <交出方宿主> 交出）。
   先现跑 pre-apply trace 并向我出示 apply 确认；交出方的确认不算本次放行。
   开工前先通读 change 全部文件，把发现的规格空缺或技术契约冲突/空缺一次性报告；
   实施中再遇到就停下该任务，按「暂停交回」格式报告归口，不自行补需求或绕开约定。
   交出时未提交文件：<清单，或「无」>。
   apply 完成后进入 verify 壳（含官方 verify）。本 change <命中/未命中> 复审风险信号<：命中项>；
   命中时 verify 结束给出复审三选一——本 change 由我方交来，默认交回 <交出方宿主> 复审——选定前不出归档回显；
   同宿主子代理审查不能替代异宿主复审。交出复审前默认提议提交。
   勾选按任务原文执行验证；只能由人做的验证不勾选，标「待人工验证」交给用户。
   ```

5. **交出后。** 本会话停止对该 change 的写入，可以继续只读答疑。不自动启动接手方。
6. **接手方先核对现场。** 收到接续或返工提示词时，先确认提示词里的提交号与现场一致、提到的复审组与未勾选任务
   确实在 tasks.md 里；对不上就停下报告，不凭提示词里的描述去实施或返工（真实运行：复审记录没写入，
   返工提示词却已到手——接手方拒绝凭描述返工，是正确做法）。

## 三、实施中的偏差归口与暂停交回

实施方（任一宿主）在 apply 中，或复审方在复审中，把发现分三类：

| 类别 | 判别 | 处理 |
|---|---|---|
| **A 实施缺陷** | spec 已写清，实现没做到（漏校验、错误边界、测试不过） | apply 中：实施方就地修；复审中：经确认追加返工任务（第四节） |
| **B 规格空缺** | 不同实现会产生不同的可观察行为，而 Released PRD / spec 没有裁决 | 停相关任务，不追加返工任务；回 valkyrja-prd 讨论/决策 → 发版 → rebaseline（V2.5 欠账门与 V4.0 联锁照常） → 必要时修订 change artifacts |
| **C 技术契约冲突或空缺** | 现有 ADEC / 共享契约与可行实现互斥，或实现需要的工程约定没有任何 ADEC 规定 | 停相关任务；回 valkyrja-arch 裁决，必要时更新 design/tasks；未经裁决不绕开约定、不自定约定 |

**C 类的边界**：跨 change 的工程约定（会落进数据或被后续 change 依赖，如存储格式、派生参数、运行与测试命令）
铸 ADEC；只影响本 change 内部的工程细节，由规划方经官方 update workflow 补进 design，不铸 ADEC——
不是 ADEC 没写的都要升级。

**拿不准是 A 还是 B/C 时按 B/C 处理**：停下问，不按 A 自行修。
任何一方都不得把「我推测合理」写成需求或决策。
**归口指技能，不指宿主**：裁决可在任一宿主用 valkyrja-prd / valkyrja-arch 进行，由用户选；
宿主怎么选是用户偏好，不是规则。

**不需要裁决的情况**：
- change 规划文件与既有 PRD / ADEC 不一致，而权威里**已有答案**（命令写错、引用错等）——不暂停等裁决；
  当前写者经确认用官方 update workflow 修正，重跑 pre-apply，并**单独提交**，提交信息写明依据与用户确认。
  **排除**：修正若会改动本 change 的 Covered-FRIDs 之外的需求（例如 MODIFIED 别的 change 负责的需求），
  就不是直接修正——内容有答案，但「由哪个 change 承载」是 decompose 的事，须经 decompose 收编（基线标跨 change）
  或例外记录裁决；trace V4.11 对这种 MODIFIED 报警（真实运行：补「口令」的 MODIFIED 越出覆盖范围，trace 全过）。
- design 里标「无决策背书，不构成约束」的候选做法：指它**不构成项目级约束**（别的 change 不受约束、
  trace 不执法、以后可替换），**在本 change 内仍是实施方照做的计划**。只在两种情况下升级：
  与 PRD / ADEC 冲突（C），或它决定了验收可观察的行为（B）。

**暂停交回**（实施方遇到 B/C 时输出，供用户拿去裁决；接手方在 apply 前被规划自检拦下时同样用本格式，
标题写「Apply 未放行：<change-name>（规划自检）」）：

```text
## Apply 已暂停：<change-name>（任务 <x.y>）
类别：<B 规格空缺 | C 技术契约冲突或空缺>
进度：<已勾选/总数>；已完成：<任务号>；受阻：<任务号>（未勾选，已写代码 <有/无> 留在工作区）
证据：<需求或 ADEC 原文 + 路径；冲突的 design/tasks 位置；命令输出>
待裁决：<一句话问题>；可选做法：<列出，不替用户选>
归口：<valkyrja-prd | valkyrja-arch>，可在任一宿主进行：
  Claude Code <`/valk:prd` | `/valk:arch`>；Codex <`$valk:valkyrja-prd` | `$valk:valkyrja-arch`>
恢复：裁决落盘并提交后，由裁决方输出恢复提示词（下方格式）
交给另一宿主处理（把本段整段粘过去）：
<另一宿主的 spec 调用名> 处理这份暂停报告：<本报告全文>
```

**处理暂停报告**（接收方，通常是另一宿主）：报告中的分类是实施方的判断，不一定准；用户只需整段转贴，
不必自己分诊。接收方逐条复判——需要裁决 / 已有权威可答（按上文修正）/ 无需升级（按 design 照做）——
需要裁决的经确认走 valkyrja-prd / valkyrja-arch；最后输出**一段**合并的恢复提示词交回实施方。

**恢复提示词**（裁决方输出，开头用实施方调用名）：

```text
<实施方调用名> next：继续 change <change-name> 的 apply。
裁决：<DEC/ADEC 编号与路径>，结论：<一句话>；按原文实现，不另选方案。
先用官方 update workflow 修订受影响的 design/tasks（经确认），再现跑 pre-apply trace 并出示 apply 确认。
<验证命令>。完成后照常进入 verify 壳。
```

规划文件在复审或裁决后被修订的，一律重跑 pre-apply trace（不只是 validate）再继续。

## 四、复审（review）

**定位**：只读分析 + 经确认写复审记录（含 A 类返工任务）。**建议性，不是门禁**：
归档门禁不变，没做复审也可以归档。**真的做了复审就写记录，无发现也写**；
没做就不写，不预留占位、不补写。

**何时主动给出**：verify 壳结束后现算风险信号，任一命中就说出命中的是哪条，并给出复审三选一，
每个选项附可直接粘贴的提示词：

- Requirement Authority 的覆盖 FRID 含 `SEC-*` 或 `NFR-*`；
- design.md 引用了共享接口契约（`契约名@版本`）；
- `.openspec.yaml` 含 `retire_capabilities: true`。

| 选项 | 何时作默认 | 说明 |
|---|---|---|
| 交另一宿主 | 本 change 由另一宿主交来（当前会话从交出提示词或返工提示词开始接手） | 异构独立判断，独立性最好 |
| 本宿主新会话 | 本 change 全程在本宿主上（项目以前用过几个宿主不算） | 报告里注明独立性较弱 |
| 跳过 | — | 复审是建议，用户选跳过即进入归档壳 |

选定前不出示归档确认回显。同宿主子代理审查不算异宿主复审，不管宿主环境有没有审查插件。
未命中不主动建议，verify 结束直接给归档的下一步；用户要求复审随时可做，不以「风险低」劝阻。

```text
<复审方调用名> 复审 change <change-name>（实施方：<宿主>）。
命中风险信号：<列表>。范围：<base>..<提交>（未提交时写「工作区」并说明原因）。
官方 verify：<结论与时间，或「未跑」>；这是实施方的自述，复审方自行判断是否补跑。
只能由人做的验证：<列表与命令，或「无」>，由用户执行，不在复审方的职责内。
按 cross-host.md 第四节输入读取，不以实施方的报告或自评作证据；
报告后经我确认写复审记录，并把不阻塞的备注按第一节分流；有 A 类返工时输出交回实施方的提示词。
```

复审提示词**只给范围与权威来源**。实施方若附上自己的关注点，必须标明「仅供参考、不限定范围，
先独立审查再对照」——复审的价值在于发现实施方没想到的地方。

**谁来审**：按上表选定；无论哪种都建议开新会话，避免与写规划或写实现的上下文共享盲区。
复审方在同一工作区只读即可。

**输入**（按需读取，不读实施方的聊天或自评当证据）：

1. Requirement Authority 列出的覆盖 FRID，在 Released PRD 中的原文（沿唯一 API 读取）；
2. spec delta、design.md（含 `依据:` 标注）、tasks.md；
3. 代码 diff：范围由用户指定，或现算为「change 目录首次提交的父提交 .. 当前工作区」；
   范围拿不准先问；
4. 测试与官方 verify 结果：本会话可安全执行的就现跑；旧结果标为带时间的历史结果。

**报告**（完整报告在对话里出）：顶部一行总账；每条发现写类别（A/B/C）、`文件:行`、
对应的 FRID / Scenario / ADEC、证据与建议改法；结论三选一——**无阻塞发现** /
**需返工（A）** / **需裁决（B/C）**。复审方不改代码、不改 spec artifacts（复审记录除外）。
报告后、会话结束前，不阻塞的备注按第一节分流落盘（各经对应技能确认），并在复审组结论行注明去向。
- **分类自检**：一条返工若要求实施方「选择一种工程做法」，而不是按已有权威修正或按 design 照做，按 C 类归口，
  不写成 A 类返工（真实运行：「不设 PYTHONPATH 也能跑测试」被写成 A，实为测试如何找到模块的约定空缺）。
- **磁盘上看不到的流程历史如实写「无法确认」**：某次修改是否经用户确认、是否有过暂停报告，看不到证据时不下结论
  （真实运行：把「修正没单独提交」说成了「实施方擅自修改」）。

**复审记录（特权，经确认）**：每次真的做完复审，回显将追加的复审组全文与目标 tasks.md 路径
（有 A 类返工时附每条对应的发现与证据），用户确认后**只追加**到 tasks.md 末尾：

```markdown
## N. 复审（第 k 轮，<复审宿主>，YYYY-MM-DD）

复审范围：<base>..<提交>；结论：<无阻塞发现 | 需返工 | 需裁决（阻塞任务 x.y，归口 prd/arch）>[；备注已记入 <归宿>]

- [ ] N.1 <可验证的改法>（依据：<文件:行>；<FRID 或 Scenario>）
```

- `N` 取现有最大组号 + 1。结论行是**普通文字、不是复选框**，不影响 `next` 的勾选比例现算；
  只有 A 类返工写成未勾选任务，无发现或只有 B/C 时组内没有任务行。
- 不改既有任务、不取消已勾选项。已勾选任务的文字与随后的裁决或 design 不一致时，不改原文，
  在复审组结论行或归档回显里注明以哪个权威为准。
- 复审组**提交前**发现记录有误（分类错、与随后的裁决冲突），可经确认原地改写，结论行注明改写原因；
  **提交后**只追加新组更正，不改写或删除旧组。
- **保护性行为**（防泄露、防回退、权限、并发）的返工任务，写明实施方可自行执行的验证条件，
  如「删掉该保护后测试应失败」；复审方核对时复做（真实运行：返工测试把被测函数整个替换掉，变异验证才发现，多跑了一轮）。
- **顺序：报告 → 回显复审组请确认 → 写入 → 提议单独提交复审记录 → 之后才给交回实施方的提示词。**
  记录没写入时不给交回提示词，免得用户先贴了提示词、记录却没进磁盘（真实运行：两者同在一条消息里，
  用户直接复制了提示词，复审组没写入，实施方拿不到返工原文）。
- 有 A 类返工时 `next` 现算为「apply 进行中」，交回提示词点名返工组编号与记录提交号，完成后照常 verify 壳。
- **返工核对算新一轮复审**：实施方完成返工后，复审方核对返工即第 k+1 轮，范围写返工任务号，
  照样经确认写记录（如「复审范围：返工 5.1；结论：无阻塞发现」）。
- **B/C 类**不写任务，按第三节归口，结论行写明被阻塞的任务编号与归口。
- 用户拒绝写入时只在对话里报告；记录是 AI 写的**复审痕迹，不是正确性证明**，也不构成归档放行条件。

> CLI 层已实测（2.0.0）：官方 apply 的任务接口识别追加组的未勾选项，结论文字不计入进度
> （见 openspec-compatibility.md 第六节）；真实运行中两个宿主的官方 apply 都按追加的返工组完成了返工。
> 交回提示词里仍点名返工组编号。

## 五、诚实边界

- 交出与复审都是**约定级**：用户直接在另一宿主调用官方 apply 时本技能无法拦截，
  与 SKILL.md「已知治理缺口」同一性质。
- 单写者靠约定，没有锁；快照与核验只在用户选了 host-handoff 时才有。
- 复审通过不是正确性证明，也不替代 trace、官方 verify 或归档确认。
